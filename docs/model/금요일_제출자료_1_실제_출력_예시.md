# 금요일 제출 자료 1 실제 출력 예시

담당 하경흠 · AI 모델/알고리즘

작성 및 검증 기준일은 2026년 11월 13일이며, 교수님 미팅은 같은 날 오전 10시 KST입니다. [중국어 원문](friday_01_real_output.md)을 바탕으로 작성한 팀 공유용 한국어 문서입니다. 중국어 원문과 실험 데이터는 변경하지 않았으며, 번역 과정에서 모델이나 평가기를 새로 실행하지 않았습니다.

문서에서는 검증 상태를 구분합니다. **이번 검증에서 확인**은 중국어 원문을 검증할 때 Git 객체, 파일 또는 CPU 검사로 확인한 내용입니다. **기존 기록**은 과거 파일의 내용을 확인했으나 원 실험은 재실행하지 않았다는 뜻입니다. **추가 확인 필요**는 증거가 부족한 항목, **가설**은 가능한 설명, **향후 계획**은 아직 실행하지 않은 작업입니다. 명령, 종료 코드와 상세 증거는 [검증 보고서·중국어](verification_report.md)에 있습니다.

**이번 검증에서 확인한 내용**은 다음과 같습니다. 고정 커밋이 존재하며 representative_inference의 9개 파일을 `git show`로 읽을 수 있습니다. `config.name=nf4_prompt_v1_first`, `quant=nf4`, `adapter_source_run=null`입니다. Metrics에는 `retry_count=0`, `format_repair=false`, `schema_valid=true`, `strict_schema_valid=true`가 있습니다. Provenance의 `source_run`은 `runs/nf4_prompt_v1_first`이며, `parser_fill=false`, `edited=false`입니다. 이 값들은 각각의 원본 파일에서 확인했으며 누락된 필드를 임의로 추가하지 않았습니다.

**기존 기록**인 `provenance.selection_rule`은 수정 Prompt 조건에서 가장 먼저 완료된 Base NF4의 첫 응답을 대표 예시로 선정했다고 설명합니다. 선정 기준은 Strict Schema 통과이며 가장 높은 의미적 점수가 아닙니다. 당시 선정 과정 전체를 별도로 재구성한 것은 아닙니다.

`raw_output.txt`는 끝에 `<turn|>`가 있는 원시 생성 텍스트이며 token ID 파일이 아닙니다. `decoded_output.txt`는 이 종료 표기를 제거한 파싱 가능한 텍스트입니다. `parsed_output.json`은 해당 JSON의 파싱 결과입니다. 검증에서 두 JSON의 내용이 같고 필드 보충이 없음을 확인했습니다. 생성 token ID는 원 실행의 `first/generated_ids.json`에 별도로 있습니다. `metrics.json`은 진단 결과이며 모델 예측 자체와 구분합니다.

## 입력과 출력 필드

**이번 검증에서 확인한 내용**으로, `messages.json`의 user 메시지는 이미지 참조 1개와 과제 설명 1개로 구성됩니다. 이미지는 `source/integrated_annotation_sample/images/view_F.png`입니다. 과제 정보는 `item_id=sample_front_001`, `view=F`, `input_type=single_image`, `intent=follow_visible_road_forward`, `temporal_sequence=false`, `future_event_reference=false`입니다. PNG 헤더에서 원본 가로 1920, 세로 1080을 확인했으며 이미지 SHA-256이 input_manifest.json과 일치합니다.

System 메시지는 `prompts/modified_system_full.txt`와 같으며 공통 관계 규칙과 전체 Schema를 포함합니다. 공개된 messages.json과 렌더링된 prompt.txt를 검토한 결과 C polygon, GT 좌표, 장면별 정답, 다른 시점의 이미지나 미래 Frame은 없었습니다. view_F Annotation에서 추출한 실제 Object/Region ID도 이 텍스트에서 발견되지 않았습니다. `audit/input_and_model_verification.json`에도 해당 run의 `image_count=1`, `gt_identifier_hits=[]`가 기록되어 있습니다. C의 개념을 설명한 공통 문장은 정답 polygon과 구분합니다.

이 확인은 공개된 요청과 입력 감사 자료에 한정합니다. 원 infer.py가 공개되지 않아 실제 실행 당시의 모든 내부 동작까지 이 자료만으로 증명할 수는 없습니다. 근거는 고정 커밋의 [messages](https://github.com/Spatzlyn/262RCOSE45700/blob/ef1ed254d4bbcb15d66c0ec96a02861ef1e7c681/kakao_dryrun/representative_inference/messages.json), [prompt](https://github.com/Spatzlyn/262RCOSE45700/blob/ef1ed254d4bbcb15d66c0ec96a02861ef1e7c681/kakao_dryrun/representative_inference/prompt.txt), [input_manifest](https://github.com/Spatzlyn/262RCOSE45700/blob/ef1ed254d4bbcb15d66c0ec96a02861ef1e7c681/kakao_dryrun/representative_inference/input_manifest.json)입니다.

명세서의 설명용 JSON과 실제 `integrated-sample-0.2` 구조는 다릅니다. 백엔드는 실제 Schema를 기준으로 처리하고, 설명용 예시에 맞추어 원 예측의 필드명을 변경하지 않습니다.

| 개념 | 실제 필드 | 실제 출력 |
|---|---|---|
| objects | `track1.objects` | 5개 객체. object_id, class, bbox_xyxy_norm, 역할과 배치 속성 포함 |
| regions | `track1.regions` | 모델이 생성한 빈 배열. Region 인식 성공을 뜻하지 않음 |
| scene | `track1.attributes` | traffic_direction, direction_match, 좌우 sidewalk |
| relations | `track1.relations.R1`부터 `R4` | 모두 A. object_ids, region_ids와 역할별 근거가 비어 있음 |
| actions | `track1.actions` | MONITOR_AHEAD, no_condition. based_on은 R1부터 R4 참조 |
| 다른 Track | `track2`, `track3` | missing_input. 해당 성능을 계산할 수 없음 |

예를 들어 `obj_2`는 `car`이며 Box는 `[0.36, 0.29, 0.48, 0.47]`입니다. R1부터 R4는 모두 A이며 유일한 대응은 `MONITOR_AHEAD / no_condition`입니다. 이는 원값의 발췌이며 전체 내용은 파싱 결과에 있습니다.

## 좌표와 근거 ID 확인

해당 출력의 `bbox_xyxy_norm`은 이미 원본 이미지 기준 0부터 1 사이의 xyxy입니다. **다시 1000으로 나누거나 x와 y를 바꾸지 않습니다.** 기존 감사에는 `no axis swap`, `no /1000`이 명시되어 있습니다. 이 결론은 검토한 출력에만 적용하며, 다른 box_2d 형식을 도입할 때는 별도 확인이 필요합니다.

원본 크기와 Box 수치는 **이번 검증에서 확인**했습니다. 픽셀 환산식은 `x_pixel=x_norm*1920`, `y_pixel=y_norm*1080`입니다. obj_2의 픽셀 Box는 `[691.2, 313.2, 921.6, 507.6]`입니다.

**기존 기록**인 audit/coordinates.json에는 `processed_hw=[576,1056]`, `resize_only=true`, `crop_or_letterbox=false`, `no axis swap`, `no /1000`이 있습니다. audit/processor_coordinate_verification.json도 처리 후 세로·가로 576×1056, `no offset`, 실제 시각 soft token 264개, padding patch 144개를 기록합니다. Budget 280은 실제 시각 token이 정확히 280개라는 뜻이 아닙니다. Patch padding을 원본 좌표의 이동량으로 처리하지 않습니다. 이번에는 처리기를 다시 실행하지 않았으므로 새 전처리 실측 결과라고 부르지 않습니다.

근거는 [좌표 감사](https://github.com/Spatzlyn/262RCOSE45700/blob/ef1ed254d4bbcb15d66c0ec96a02861ef1e7c681/kakao_dryrun/audit/coordinates.json)와 [처리기 감사](https://github.com/Spatzlyn/262RCOSE45700/blob/ef1ed254d4bbcb15d66c0ec96a02861ef1e7c681/kakao_dryrun/audit/processor_coordinate_verification.json)입니다.

존재하지 않는 ID를 참조하는 오류는 없고 엄격한 validator를 통과했습니다. 다만 관계 근거는 모두 빈 배열이므로 참조 형식이 유효하다는 것과 근거 연결이 정확하다는 것은 다릅니다. Action의 based_on이 존재하는 R1부터 R4를 참조해도 관계나 대응의 정답을 보장하지 않습니다.

## 진단 결과와 미팅 설명

| 항목 | 실제 결과 | 해석 |
|---|---|---|
| Strict JSON과 Schema | 통과 | retry_count=0, format_repair=false |
| 객체 매칭 | 5개 예측 중 4개 매칭, Draft 객체 16개 | 4/16은 매칭 수의 설명이며 F1이 아님. 정답 coverage가 불완전하면 미매칭 예측을 바로 오탐으로 처리할 수 없음 |
| R1 | Draft P, 예측 A | 점유 Draft와 다름. C와 접지 범위의 사람 검수 필요 |
| R2 | Draft U, 예측 A | 정보 부족과 확인된 부재를 혼동했을 가능성. 모델 내부 원인으로 확정하지 않음 |
| R3 | Draft P, 예측 A | 일부 해당 차량은 매칭되었고 가림 근거는 비어 있음. 가림 근거 연결 실패는 검증할 가설 |
| R4 | Draft P, 예측 A | 통행 공간 제약 Draft와 다름. 단일 Draft로 실패 원인을 확정할 수 없음 |
| 대응 | 실패, required group 0/4 충족 | 현재 pair는 reference allowed set 밖에 있음. 명시적 forbidden pair 위반과 구분 |

미팅에서는 다음과 같이 설명할 수 있습니다. 모델이 차량 5개를 검출했고 그중 4개가 Draft 객체와 매칭되었습니다. 그러나 네 관계의 근거를 비워 두고 모두 A로 판단하여 전방 관찰만 제시했습니다. 현재 Draft에서 요구하는 대응을 충족하지 못했습니다. 출력 사실은 확인했지만 구체적 원인은 라벨 검수와 다른 장면에서 추가로 확인해야 합니다. 형식 통과는 의미적 정답을 뜻하지 않으며, 이 결과를 QLoRA의 개선으로 해석하지 않습니다.

독립 장면은 1개이고 Human Reviewed 장면은 0개입니다. 모든 수치는 Draft 진단이며 공식 V3/V4/V5나 신뢰구간을 계산하지 않습니다. **이번 검증에서 확인한 내용**으로, 저장된 예측·Schema·reference와 원 evaluate.py로 CPU 검증 및 재채점을 수행하여 diagnostics와 action_rules가 기존 결과와 완전히 같음을 확인했습니다. 객체 4개 매칭, 관계 0/4, Action=False이며 종료 코드는 0입니다. 기존 테스트 30개도 실행하여 통과했습니다. 사용 환경은 Conda base Python 3.8.15와 표준 라이브러리이며 Gemma 실행 환경을 검증한 것은 아닙니다. 전체 명령과 출력은 검증 보고서에 있습니다. 새 모델 생성은 수행하지 않았습니다.

로컬의 주요 텍스트 25개는 CRLF/LF를 통일하면 고정 커밋과 내용이 같지만 바이트 hash는 다릅니다. 로컬 CRLF 파일의 hash를 커밋의 원본 LF hash로 제시하지 않습니다. 실험 파일은 변경하지 않았습니다.

## 백엔드 전달 자료와 담당 범위

우선 raw_output, decoded_output, parsed_output, config, input_manifest, provenance, 기존 metrics, 적용 Prompt와 Schema를 전달합니다. Reference는 별도 채점 단계에서만 사용하고 모델 요청에 넣지 않습니다. 이 자료는 과거 실제 실행 예시의 인계이며 생산 API 완성을 의미하지 않습니다.

모델 담당자는 예측과 Run 기록을 생성합니다. 백엔드는 자동 채점·저장·API를 담당하고, 채점 결과를 모델 담당자에게 전달하여 오류 분석에 사용합니다.

현재 config.name으로 기존 run을 식별할 수 있지만 팀 공통 Run 구조가 확정된 것은 아닙니다. 새 Pilot은 run_id, sample_id, attempt_index, 실패 상태와 버전을 별도로 기록해야 합니다. 기존 예시가 최종 API 형식을 이미 충족한다고 표현하지 않습니다.

PDF와 샘플 패키지 사이에는 Roadside/Obstacle 대응 규칙 차이가 있습니다. PM·데이터·백엔드가 팀 공통 기준 규칙 버전(canonical rule version)을 확정해야 합니다. 그전까지 기존 패키지는 재현 가능한 진단에 사용하며 PDF 최종 규칙을 완전히 준수한 결과라고 부르지 않습니다.
