## 고정할 Base 조건 제안

역사적 대표 예시는 Base NF4 `nf4_prompt_v1_first`, `adapter_source_run=null`, 형식 Prompt 수정 후 첫 응답입니다. 저장된 결과와 CPU 재채점은 Strict JSON/Schema 통과, 예측 객체 5개, Draft 매칭 4개, 관계 0/4, Action=False로 같습니다. Human Reviewed 장면은 0개입니다. 같은 Draft 한 장면을 사용한 QLoRA 5-step smoke는 기존 실행·재로드 기록일 뿐, loss 감소로 일반화 개선을 증명하지 못합니다. 공식 Benchmark 결과로 해석하지 않습니다.

새 Pilot은 형식 통과를 확인한 Base NF4 설정에서 시작하고 QLoRA adapter는 로드하지 않는 방안을 제안합니다. 이는 새 Pilot의 기준이며 기존 BF16 baseline을 대체하거나 이름을 바꾸지 않습니다.

| 설정 | 제안 값과 근거 |
|---|---|
| 모델 | google/gemma-4-E4B-it |
| revision | 4ecc2ba63bcac23ba4a767fc87025b1450f84c9c |
| 양자화 | NF4 4-bit, double quant, BF16 compute |
| attention | text/vision SDPA, audio eager. 기존 설정 유지 |
| batch | 1, 한 번에 이미지 1장, cpu_offload=false |
| 생성 | do_sample=false, seed=42, max_new_tokens=4096, enable_thinking=false |

| Schema | source/integrated_annotation_sample/schema/prediction.schema.json |
| 이미지 처리 | RGB, soft-token budget 280, 저장된 processor 설정 유지 |

## 실행 순서와 전달

아래는 **일요일 후속 작업을 위한 계획**이며 아직 수행하지 않았습니다.

1. 태문님에게 6장을 받으면 sample_id, source_group, 이미지 hash, 원본 크기, intent, 데이터/라벨 버전과 검수 상태를 기록합니다. 정답이 들어가지 않는 별도 입력 manifest를 만듭니다.
2. 원 추론 코드를 확보하고 확인하거나 새 구현임을 명시합니다. 팀 GPU에서 로딩 및 이미지 한 장 smoke를 확인합니다. 환경·코드가 바뀌면 새 버전을 기록하고 과거와 완전히 같은 실행이라고 부르지 않습니다.
3. PM·데이터·백엔드와 규칙 및 Schema를 확정합니다. 규칙을 수정하면 prompt/reference/evaluator도 함께 버전 관리합니다. Pilot 조정 자료는 Train/Dev로 관리하며 조정 후 최종 Test로 사용하지 않습니다.
4. Base 설정을 고정한 뒤 manifest 순서로 6장을 실행합니다. 한 장이 끝나면 저장하고 혜승님께 전달합니다. 전체 추론이나 오류 분석 완료를 기다리지 않습니다.
5. 첫 응답과 재시도를 별도 보존합니다. 모델이 누락한 필드를 채우지 않습니다. 전체 Markdown fence만 제거하더라도 파생 파싱 결과로 구분하고 첫 Strict 형식 실패 상태를 남깁니다.
6. 백엔드는 검수된 라벨 항목을 채점합니다. Missing·미검수 항목을 강제 채점하지 않으며 Unknown은 유효한 정답입니다. 모델 담당자는 채점 결과를 받은 뒤 오류표를 작성합니다.

Timeout은 smoke에서 지연시간을 확인한 뒤 6장 실행 전에 정하고 기록합니다. 검증하지 않은 숫자를 임의로 제시하지 않습니다. OOM, Timeout, 파싱 실패와 정상 완료를 모두 남기고 실패한 문항을 manifest에서 삭제하지 않습니다.

다음 디렉터리는 전달 형식 제안이며 구현된 추론 입구가 아닙니다.

```text
runs/<run_id>/
  run.json
  input_manifest.jsonl
  config.json
  prompt.txt
  schema.json
  <sample_id>/attempt_00/
    raw_output.txt
    decoded_output.txt
    parsed_output.json
    status.json
```

run.json에는 model revision, code commit, prompt/schema/data/label/split 버전과 hash, seed, 실제 의존성과 GPU를 기록합니다. status.json에는 시작·종료 시간, 첫 응답/재시도, Strict JSON/Schema 상태, 예외 종류와 오류 설명을 기록합니다. 파싱할 수 없으면 임의 parsed_output을 만들지 않고 파일이 없는 이유를 남깁니다. 재시도는 attempt_01로 저장하고 attempt_00을 보존합니다.

6장 후속 작업의 완료 기준은 다음과 같습니다.

- sample_id 6개가 모두 manifest에 있고 각 문항에 최소 1개의 attempt 상태가 있습니다.
- 성공 응답은 raw/decoded/parsed를 보존합니다. 파싱 실패는 raw, 생성된 decoded, status/error를 보존하고 parsed를 만들지 않습니다.
- 성공, OOM, Timeout, JSON 실패와 Schema 실패가 모두 기록됩니다. 첫 응답과 재시도를 구분하며 실패 기록을 삭제하지 않습니다.
- Config, 전체 Prompt, Schema, 실제 환경, 코드 버전, 데이터/라벨/split 버전과 hash가 있습니다.
- 각 결과나 실패 기록은 생성되는 대로 백엔드에 전달합니다. 실행할 수 없으면 차단 사유를 전달합니다.

## 백엔드와 채점 범위

현재 샘플 평가기는 기하 매칭, 근거 검사와 대응 규칙 진단을 제공하지만 production benchmark aggregation은 구현되어 있지 않습니다. 샘플 evaluate.py를 전체 V1부터 V14의 생산 채점 서비스로 부르지 않습니다. 공식 집계와 API는 백엔드가 담당합니다.

공통 6장은 소규모 진단용입니다. 독립 검수를 마치지 않았거나 4개 관계와 3개 상태의 12개 조합을 확보하지 못하면 공식 V5=N/A입니다. 표본 수, 검수 범위, 미충족 조합과 제외 사유를 함께 제시합니다.
